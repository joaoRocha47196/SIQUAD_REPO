ecv/1_ecv_builder/__init__.py

1 · ECV builder: inventory + specification -> complete ECV declarations, then review by layers.

Receives: the inventories of a domain (module 0) and its definition (dominio.json: sources, uses, scenarios).
Needs: the internal specification (specs/ecv_specs.md, built from specs/ by specs_bundle.py), the build process
(build_process.json), the reference declarations (examples and other accepted domains) and the review notes.
Produces: one generation request to the LLM (phase G: the complete declarations and the mapping of every inventory
item); then, for each review layer A to F, the checks of the layer and the change requests that correct or complete it
(applied by module 2).

    build_process.py  phases, layers, principles, procedures, response format
    specs_bundle.py   the single internal specification for the LLM
    context.py        what the generation prompt receives; the uncovered inventory items of a layer
    package.py        the generation prompt and the change prompt of a layer
    reference.py      reference declarations; reused models completed with their rules
    search.py         search and similar models in a graph
    checks.py         the checks after the generation and of each layer
    workflow.py       prepare, register, request changes, accept

(sem definições públicas)

ecv/1_ecv_builder/build_process.py

The build process of a domain's declarations (build_process.json):

    0      extraction (module 0): one inventory per source
    G      generation: the complete declarations in one request to the LLM (full specification + all the inventory)
    A–F    review layers (structure, projections, plausibility, inference, functions, profiles): each layer is reviewed
           and corrected through change requests (natural language, operations, CSV tables, information from other sources)

Each phase and layer has what it is, its principles and procedure, checks, views, review questions and preferred
operations; the cycle says what happens in each stage.

ecv/1_ecv_builder/checks.py

The checks of the generation (phase G) and of each review layer (A to F).

Always:
    verification       each declaration against the specs (module 3); errors block
    cobertura          inventory items not yet in the mapping: in G, every element and rule (informative);
                       in a layer, the elements (A) or the rules of the layer's categories (B to E), and it blocks
    fusao              the domain's declarations merged with each other; a conflict blocks
    conflitosComReferencia   the domain merged over the reference declarations (examples, other domains)
G and A:
    destinosInexistentes   mapping destinations that are not a path of the declaration; blocks
    partilhadosDiferentes  a shared model that differs between two declarations; blocks
    semelhantesNoGrafo     a new USM that looks like a model of the reference (reuse it?)
G and C:  valoresAdmitidosSemRP   source elements with allowed values whose property has no RP
G and D:  coerencia               terms outside the plausible values, incompatible rules, repeated conditions
G and E:  funcoesSemelhantes      functions with the name or the parameters of a function of the reference

ecv/1_ecv_builder/context.py

The context of the prompts of module 1.

Generation (phase G) receives everything at once:
    inventory      groups, elements and rules of every source (complementary sources: only cardinalities and descriptions)
    domain data    the uses, scenarios, known mappings and metadata of dominio.json
    existing       the models and functions of the reference declarations (to reuse)
    declarations   the current declarations and mapping (when the generation is repeated)
    notes          the review notes of the domain

A review layer (steps A to F) gives a change request its slice of the inventory: the items of the layer's
categories that the mapping does not mention yet.

ecv/1_ecv_builder/search.py

Search in the graph, to confirm whether an entity already exists before creating it (no duplicates).

  search(g, text)              -> nodes whose name, key, description or alternative names contain the text
                                  (ignoring case and accents), by label;
  similar_models(g, props)     -> USM and SM whose properties (names and alternative names) overlap the given
                                  ones (Jaccard index), most similar first;
  existing_models(g)           -> every HLM, USM and SM with what the merge compares (for the step A prompt);
  existing_functions(g)        -> functions and external contexts (for the step E prompt).

Only the Graph interface is used: it works on the in-memory graph and on Neo4j.

ecv/1_ecv_builder/specs_bundle.py

The internal specification: one file with everything the LLM needs to write a declaration.

The specs in specs/ are written for people (diagrams, tables, examples taken from the example
declarations, links, the graph edges of each entity). The LLM needs the rules of the format, not the
presentation: this module builds, from the same files, a single compact text (specs/ecv_specs.md):

  - the closed vocabulary, read from the configuration (types, operators and value forms, operators per
    type, cardinalities, rule types, naming patterns, metadata SM);
  - the declaration structure (one declaration, one HLM; every section and field);
  - each ECM and ECR entity: description, attributes, sketch in the declaration, can / cannot, details,
    verifications;
  - naming, paths, catalogue and the verification codes.

Removed: mermaid diagrams, the graph edges, the generated tables of the example declarations, links and
the parts that only explain the thesis or the repository. Tables become lists. Every step prompt
includes this file in full, so the LLM can map any inventory element or rule to the right construct.

    python -m ecv specs        rewrites the file; a test checks it is up to date

ecv/1_ecv_builder/workflow.py

The cycle of a domain, as the web application and the CLI call it.

    prepare_generation(domain)                    -> LlmRequest "passo" G (prompt.md: full specification + all the inventory)
    (the LLM answers: resposta.json in the request folder, by commit or pasted in the web app)
    register_generation_response(domain, request) -> the declarations and the mapping created from the response; checks; G "em revisão"
    accept_step(domain, "G")                       -> the review layers may start
    request_changes(domain, text, layer, extra)    -> LlmRequest "alteracao": natural language (and information from another source) -> operations
    register_change_response(domain, request)
    apply_operations_to_domain(domain, ops, layer) -> operations given directly (web form, CSV, file)
    accept_step(domain, layer)                     -> the layer's checks pass: the next layer may be accepted

Nothing here talks to an LLM: a request is a folder (shared/llm_requests.py), answered outside.

ecv/3_ingestion/descriptions.py

The readable description of a rule, derived from what the rule already declares.

It adds no knowledge: it joins three parts of the rule (thesis, section "Condições de aplicabilidade"):
  - the applicability expression, which gives "Se ...", with the terms joined by "e";
  - the link to the model, which prefixes each property with the model where the rule lives;
  - the restriction, which gives "→ ..."; in a RIC, replaced by the conclusion.

Example (RIR-TEMP-REFRIG-CELSIUS, on the HLM Dispositivo):
  Se Identificacao.tipoDispositivo = TEMPERATURA e Leitura.Medicao.unidadeMedida = °C
  e Leitura.Instalacao.ambiente = REFRIGERACAO → Leitura.Medicao.valor entre -30 e 0

ecv/3_ingestion/merge.py

Merge: add the graph of one declaration to an existing graph, without duplicates.

Each declaration describes one HLM and repeats, in full, the shared models (USM Morada, SM Cliente,
...), functions and external contexts it depends on. When ingesting, each node is looked up in the
existing graph by its logical identity ('<label>:<key>'):

  - not there            -> new node, with every edge it owns;
  - there and equal      -> reused; its edges are already there;
  - there and different  -> conflict (the same entity with another definition).

"Equal" compares the node's signature: its attributes and the edges it owns. The owner of each edge
comes from graph_model.json: 'origem' (the source node) or 'regra' (the rule named in the edge's
'regra' attribute, for the LE edges that leave a shared Funcao). So a shared model with one more
property, a different composition or a changed rule is detected instead of silently summed.

With conflicts nothing is added (policy 'rejeitar' in the configuration). Planning only reads the
target through the Graph interface, so it works the same against memory and Neo4j; applying the
plan depends on the target.

ecv/3_ingestion/paths.py

Resolution of paths in the ECM structure.

A path is relative to a model (the model where a rule lives, or the HLM in a projection or a
profile) and is made of the roles of the compositions to follow, optionally ending in a property:

    Leitura.Medicao.valor      (from the HLM Dispositivo)
    Linha.numero               (from the SM Linhas)
    Linhas.Linha               (from the HLM Fatura: ends in a model, the collection)
    valor                      (from the USM Medicao)

The role of a composition is, by default, the name of the composed model; a composition may
declare another one ("papel").

ecv/3_ingestion/verification/__init__.py

Verification of an ECV declaration, before anything is materialised.

Two levels (thesis, section "Verificação da declaração"):
  1. specs: each entity on its own (required attributes, shape, names);
  2. invariants: what can only be checked with every entity loaded (I1 to I13).

An error stops materialisation; a warning does not, but is reported. I1 to I9 follow the table of
invariants of the thesis; I10 to I13 were added in this reference version (specs/declaracao/README.md).

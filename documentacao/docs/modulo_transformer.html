ecv/0_transformer/adapters/__init__.py

Adapters of phase 0: one per source format. Each one reads a source and returns an Inventory.

ADAPTERS maps the name used in dominios/<d>/dominio.json (field `adaptador`) to the function that
implements it. A source with `nomesDe` receives the English names of the terms taken from another
source (the CIUS-PT guide takes them from the schematron).

Adapters created by a request to the LLM (kind "adaptador", see ../adapter_requests.py) are modules
`a_<name>.py` in this folder with NAME (the name used in dominio.json), DESCRIPTION and adapt(path);
load() registers them next to the built-in ones.

ecv/0_transformer/adapters/cius_pt.py

CIUS-PT adapters: the semantic model guide (PDF), the schematron and the annotated UBL models.

  guide(pdf)          -> groups (BG) and elements (BT) of the semantic model, with the Portuguese name, the type,
                         the CIUS-PT cardinality (the standard's goes to the notes) and the rules mentioned by each
                         field. It is the main source of the structure: semantic, independent of the XML syntax.
  schematron(folder)  -> rules: each assertion (assert/report) with the text, the severity, the context (the group),
                         the expression (the parameter of the UBL binding) and the elements it mentions (BT-n, BG-n).
  ubl(xml)            -> syntactic groups and elements of the annotated UBL model (invoice, credit note, status
                         message): Portuguese description and cardinality of each element.

The PDF is read with `pdftotext -layout` (poppler). The English names of the terms (Seller name, Invoice
number…) are taken from the rule messages and become alternative names.

ecv/0_transformer/adapters/fm.py

FM adapters (invoicing and sales system): the Dart classes and the layout of the export records.

  dart(folder)    -> one group per class (and per enum), one element per field, with the Dart type mapped to a base
                     type; a field whose type is another class (or a list of it) keeps `tipoOrigem` = the class: a
                     composition hint for step A.
  records(xlsx)   -> one group per record (VDM, CLI, STK, ...), one element per field, with the length, the record
                     type (C, N(8.2), D, L), the remarks and, when it exists, the matching Dart property (alternative
                     name). The length gives a candidate format rule.

Only the record layout is read: the data files (Dados_Imp.txt) hold personal data and are never read.

ecv/0_transformer/adapters/json_schema.py

JSON Schema adapter (Smart Data Models): models, common definitions, properties and candidate rules.

  smart_data_models(folder) -> one group per model (`<Model>/schema.json`) and per common definition it refers
                               to (GSMA-Commons, Location-Commons, Device-Commons, ...); one element per property,
                               with the base type, the format, the description (without the "Property. Model:..."
                               prefix) and the schema.org model as source type; candidate rules for `enum` (values),
                               `minimum`/`maximum` (range), `format` and `pattern` (format) and `required` (presence).
                               Values the source only lists in the description ("Enum:'a, b'" or "Enum: [A, B]")
                               also count as allowed values.

The common definitions stay as groups of their own because in the source they already are reused sets:
natural USM candidates for step A (but step A decides).

ecv/0_transformer/adapters/text.py

Text adapter: a description of a domain in natural language (Markdown or plain text).

  markdown(path) -> one group per section (`## Name`), one element per item of a list in that section
                    (`- name (type, cardinality): description. Valores: a, b, c`), one candidate rule per sentence
                    that states an obligation or a condition ("deve", "só", "se ... então", "não pode", ...);
                    the whole text stays in the inventory (fonte.texto), so the generation reads it as written.

Nothing is required of the text: a section without a list is only a group with its description, and a text without
sections is one group. The structure is a hint; the generation (phase G) decides the ECM and the ECR.

ecv/0_transformer/inventory.py

The inventory: the neutral intermediate format each source is extracted into (phase 0).

An inventory has three lists, each item with its origin (file and location in the source):

  groups    sets of elements with their own meaning in the source (a BG of CIUS-PT, an FM record, a
            Dart class, a Smart Data Models model or common definition);
  elements  the atomic information (a BT, a field, a property): name, description, base type,
            cardinality, owning group and the allowed values when the source lists them;
  rules     what the source declares as rules (schematron assertions, enum, minimum and maximum,
            formats, required), with the text, the elements they mention, the severity, the category
            and the probable ECR nature (RE, RP, RIR, RIC or function), a hint for steps B to E.

The inventory is not ECM yet: the groups are the source's and need not become submodels. Step A
decides the ECM structure from the groups and elements of every source of the domain.

The JSON file keeps the Portuguese keys of the format (read by the prompts and by the web application).
